# 记忆层与上下文窗口

记忆存在磁盘上。模型每轮只看见按预算装好的一片。全文、旧对话和更早的反馈都留在文件里，不因为窗口再变大就继续多塞。

预算以 token 计。实现能拿到当前模型的 tokenizer 时用 tokenizer。拿不到时用本文的估算，估算只用于裁剪，不用于计费。

## 五类记忆

| 记忆 | 存在哪 | 写入时机 | 磁盘上保留 | 进入提示 |
| --- | --- | --- | --- | --- |
| 线程记忆 | `projects/<slug>/checkpoints.sqlite` | 每个图步骤之后 | 恢复确认卡所需的状态，加上一条 Observation | 只带上一条 Observation，最多 400 token |
| 文稿记忆 | `brief.md`、`outline.md`、`sections/`、`meta.json`、`literature.jsonl`、`sources/` | 对应动作落盘时 | 全量。`sources/` 分 card、excerpt、archive 三截 | 按下面的切片表。archive 不进入提示 |
| 反馈记忆 | `decisions.jsonl` | 用户提出修改意见时 | 该项目里的原文，不删 | 最近 10 条，每条最多 30 字 |
| 用户画像 | 全局 `user_profile.md` | 每条反馈写入之后 | 最多 15 条偏好。用户可在窗口删除 | 整份，最多 1,200 token |
| 技能记忆 | `skills_user/` 与内置 skill | 用户同意 `propose_skill` 之后 | 全量文件 | 最多 2 份正文，合计最多 1,200 token |

检查点里不放各节正文、文献摘录和画像。关窗后再打开，确认卡来自检查点，正文来自项目目录。这样两边不会各记一份已经过时的文稿。

画像只收写作偏好：语言、读者、语气、结构、引用，以及明确拒绝的写法。不写身份、经历或其他与写作无关的推断。

去重规则：
- 第一版：去掉标点后精确匹配，同一句已存在就更新，不追加重复
- 第二版（可选）：用嵌入向量计算相似度，余弦 > 0.9 视为重复

用户已经在改稿时说过这句话，所以画像更新不再单独确认。

```markdown
language: 中文
tone: 学术、直接
structure: 总结按结论归类，不按论文逐篇罗列
citation: 相关工作按主张组织
rejects:
  - 不要把检索词直接写成标题
```

技能文件可以比提示里长。装载时只注入 description 和正文的前 600 token。画像是短偏好，skill 是步骤，两者不互相替代。

## 窗口用量

模型上下文至少要有 **32,768 token**。比这小的模型不作为实现目标。

这三万二千 token 分成三块，合起来仍小于 32,768：

| 用途 | token | 理由 |
| --- | --- | --- |
| 输入提示上限 | 16,000 | 相对原先 8k 设计整体翻倍：仍以「一轮一节」为主，但摘录与当前节可以更完整 |
| 输出预留 | 4,096 | 一节约 500～1,000 字时约 1k～2k token；4,096 够写下较长一节和要旨 |
| 接口开销预留 | 4,096 | 留给对话模板、角色标记、tools schema 和框架包装，避免贴着模型上限被截断 |

16,000 + 4,096 + 4,096 = 24,192，低于 32,768，大约还剩 8,500 token。模型如果有 64k 或更长的窗口，提示仍停在 16,000。窗口变大不自动放进更多原文，否则同一份文稿在不同模型上会写出不同范围的内容。

不把 16,000 再继续加大的原因：材料放得越长，模型越容易用到中间那段不相关的原文，也越容易离开摘录自由发挥。一节的依据应该集中，并且靠在当前任务旁边。

## 16,000 token 怎么分

各切片上限相加正好是 16,000。某一块没写满，空出来的 token 不转给别的切片，以免实现时互相挤占、上限失真。相对原先 8k 表整体 ×2。

| 切片 | 上限 | 大约相当于 | 取值理由 |
| --- | --- | --- | --- |
| 系统说明 | 1,000 | 固定短文 | 只放规则：一轮只调用一个工具、没有摘录就不写、不能编造文献。动作清单由 function calling 的 tools schema 提供，不必在正文里再抄一遍 |
| `brief` | 800 | 400 字 | 够放下题目、读者和几条约束。更长的说明属于文稿正文，不放在 brief 里 |
| 大纲 | 400 | 200 字 | 大约 15 到 25 个标题。大纲只负责定位当前节，不携带各节内容 |
| 节状态与要旨 | 800 | 20 条、每条 20 字 | 20 字只能写成一个短语，避免要旨变成第二节正文。超过 20 节时，多出来的只留 id 和状态 |
| 文献卡片 | 800 | 12 条短卡片 | 这是提示里的索引，不是确认卡，也不是 `sources/*.md` 里的 `## card`。每条只有 id、缩短的标题、年份、依据类型。摘要正文在摘录里 |
| 用户画像 | 1,200 | 约 15 条短句 | 15 条覆盖语言、读者、语气、结构、引用和拒绝项。再多就应当变成 skill，而不是继续堆偏好 |
| 最近反馈 | 600 | 10 条、每条 30 字 | 10 条覆盖还没收进画像的新意见。30 字够认出是哪一条；原文在 `decisions.jsonl` |
| skill 正文 | 1,200 | 2 份、每份约 300 字 | 一份对应本轮内置动作，一份对应用户自己的做法。第三份很少改变这一轮，却会占掉摘录的位置 |
| 上一条 Observation | 400 | 约 200 字 | 只保留上一轮的结果，例如「总结已写成草稿」。不保留更早的 tool call 或理由文本 |
| 当前节 | 2,000 | 约 1,000 字 | 一轮的修订单位是一节里的一块，不是一整章。文件更长时，提示只带正在改的这一段，其余用要旨代替 |
| 摘录 | 6,800 | 3 篇合计；单篇裁剪上限 2,400 | 这是最大的一块，因为正文必须跟着摘录写。三篇同时接近上限时先按单篇 2,400 截，再保证合计不超过 6,800 |
| 合计 | 16,000 |  |  |

单篇摘录上限 2,400 token，是为了放得下一篇较长的中文摘要或开放获取节选（大约 800～1,000 字量级）加上标点和引用标记，或一篇更完整的英文摘要加上格式开销。

`draft_section` 和 `revise_section` 的工具参数里，`source_ids` 最多 3 个（schema 用 `maxItems: 3`）。点名超过 3 个时，按输入顺序保留前 3 个，并在提示里注明其余未展开。

当前节超过 2,000 token 时，不把整节截成头尾两段。窗口要求用户先点中要改的段落，提示里放该段及其前后各约 200 字，总量仍不超过 2,000 token。这样修订对着用户点的位置，而不是对着被截断的残段。

实现常量见 `memory/budget.py` 的 `PROMPT_TOKEN_BUDGET` 与 `BUDGET`。

## 估算

没有 tokenizer 时，按这个规则估算，并向上取整：

- 一个中日韩统一表意文字计 2 token。常见中文分词下，一个汉字经常是 1.5 到 2.5 token，取 2 作为中间偏紧的估计，避免按「1 字 1 token」把实际用量算小。
- 连续的 ASCII 每 4 个字符计 1 token。
- 其他非 ASCII 字符每个计 2 token。

表里的「大约多少字」按汉字估算。英文按 4 个字符计 1 token，同样 2,400 token 放得下更长的英文摘录。

## 谁不进提示

这些内容留在磁盘或界面上，即使用户把模型换成更长上下文，也不自动加入：

- `sources/` 的 archive，也就是开放获取全文里摘录以外的部分
- 非当前节的正文
- 第二条及更早的 tool call 与理由文本
- `decisions.jsonl` 里除最近 10 条以外的原文
- 第 4 篇及以后的摘录
- 第 13 条及以后的已确认文献卡片。这些记录仍在 `literature.jsonl`
- 确认卡上尚未写入 `literature.jsonl` 的候选。候选只在界面上给用户勾选

裁剪如果仍然超过某一格的上限，只截断那一格，并在该格末尾加上「已截断，全文在文件中」。不删 `brief`、用户画像和文献 id。当前节按上面的段落规则装入，不从中间硬切。
